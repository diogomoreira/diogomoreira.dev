# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

> **Note for Claude Code:** The user runs the dev server themselves. Don't start `hugo server -D` automatically — check if one is already running first, or ask the user to start it.

```bash
# Development server (drafts included)
hugo server -D

# Production build (runs prebuild + hugo + pagefind index)
npm run build

# Production build steps individually:
# 1. Copy photoswipe dist files from node_modules → assets/photoswipe/
npm run prebuild
# 2. Build site with minification
hugo --minify
# 3. Build pagefind search index
npx pagefind --site public
```

> **Important:** Always use `npm run build` (not `hugo --minify` directly) for production builds. The `prebuild` step copies PhotoSwipe assets from `node_modules` into `assets/photoswipe/`, which Hugo requires at build time. Skipping it causes a nil-resource build error.

New content via archetypes:

```bash
hugo new blog/my-post-slug/index.md
hugo new photos/my-album-slug/index.md
hugo new snippets/my-snippet-slug/index.md
```

Formatting:

```bash
npm run format   # prettier --write .
npm run lint     # prettier --check .  (same thing, non-mutating)
```

## Formatting

**Prettier is the only formatter, and `layouts/**/\*.html`goes through`prettier-plugin-go-template`.** `.prettierrc`sets the`go-template`parser for every`.html`file;`.vscode/settings.json`makes Prettier the default formatter on save and turns VS Code's built-in HTML formatter off, because that one mangles`{{ … }}`outright. The`.vscode/`directory is re-included in`.gitignore`on purpose — a global`~/.gitignore_global`excludes it, and the whole point is that an editor save and`npm run format` produce the same bytes.

The plugin is not a general Go-template parser, and three of its limits are load-bearing. Every one of them was found by formatting the templates and diffing the built site against the previous build — do that (`hugo -d <tmpdir>` twice, since a running dev server owns `public/`) after any change to formatting config, because **every failure below is silent: Prettier reports success and the built HTML changes.**

- **A `{{/* … */}}` comment may not contain `}}`.** The plugin's scanner is one non-greedy regex ending at the first `}}`, so a nested usage example (`Usage: {{ partial "x" . }}`) ends the comment there and the rest of the prose is parsed as real markup. Two ways that bites: a bare `<date>` or `<span>` in the prose becomes a real tag and Prettier balances it by appending `</date>` / `</span>` _after_ the file's last `{{ end }}`, emitting orphan tags into every page that calls the partial; and an `{{ end }}` in the prose is read as a real `end` and fails the parse. Every doc comment therefore writes its examples in backticks — `` `partial "post-card.html" (dict "page" $post "featured" true)` `` — and quotes bare tag names. `social.html` carries the scar and the note; it had shipped an orphan `</span>` before.
- **Whitespace directly inside an action body is dropped; whitespace outside it survives.** `class="lg:grid{{ if … }} lg:grid-cols-[13rem_1fr_5rem]{{ end }}"` formats to `…}}lg:grid-cols-…` and renders `lg:gridlg:grid-cols-[13rem_1fr_5rem]` — two broken classes, no error anywhere. Write the separator outside the action instead: `class="lg:grid {{ if … }}lg:grid-cols-[13rem_1fr_5rem]{{ end }}"`. This matters more now than it used to: most templates carry a branching class string, and the ones that do are written as a `{{ $x := cond … }}` variable interpolated whole wherever the branch is long. Same rule in attribute position, where `{{- if $external }} target="_blank"{{ end }}` loses its leading space and glues onto the preceding attribute: drop the `-` trim marker and let the newline separate — `{{ if $external }}target="_blank"{{ end }}` on its own line. A trailing or leading space in a `class` list is harmless; a missing one is not.
- **A tag may not be opened in one branch and closed in another.** `{{ if $link }}<a …>{{ else }}<div>{{ end }}` … `{{ if $link }}</a>{{ else }}</div>{{ end }}` is unparseable HTML and the plugin dies with "Found invalid node root". `layouts/partials/favorites-items.html` needs that shape — a linked list row is an `<a>`, an unlinked one a `<div>` — so it is listed in `.prettierignore` and is the one file formatting does not reach. A third instance of the same error class is cheaper to fix than to ignore: an action glued to the tag _name_, `<strong{{ if $desktop }} class="font-mono"{{ end }}>`, only needs a space after the name.

What formatting does change in the output, harmlessly: whitespace inside tags (`</a\n>`, `datetime="…"\n>`), which also shows up escaped inside RSS `<description>`; long attribute values wrapped across lines, which is why the only such value is `rel` (a space-separated token list — do not let this happen to `href`, `alt` or a `meta content`); and inline `<script>` JS reformatted under `arrowParens: "avoid"` and `trailingComma: "all"`.

`.toml` is not formatted — Prettier has no TOML parser — so `hugo.toml` and `i18n/*.toml` are held to `.editorconfig` by the `files.*` settings in `.vscode/settings.json` instead.

## Architecture

### Stack

- **Hugo** static site generator (v0.159.1 extended, required for Tailwind CSS processing)
- **TailwindCSS v4** + **DaisyUI v5** for styling — configured entirely in `assets/css/main.css` (no `tailwind.config.js`)
- **Pagefind** for client-side full-text search (index built post-hugo, served from `public/pagefind/`)
- **PhotoSwipe v5** for photo lightbox (JS/CSS sourced from npm, copied to `assets/photoswipe/` at build time)

### CSS Pipeline

`assets/css/main.css` imports Tailwind and DaisyUI via `@import`/`@plugin` directives. Hugo processes this via `css.TailwindCSS` inside `layouts/partials/css.html`, which is injected into `<head>` using `templates.Defer` (ensures the global CSS is built once across all pages). In development, the file is served unminified without a fingerprint; in production it is minified and fingerprinted for cache-busting.

**Tailwind scans the project directory directly, and this is the single most load-bearing fact about styling here.** Automatic source detection runs from the project root, so `layouts/`, `content/` and `assets/` are all read as sources; `main.css` names `layouts` explicitly as well, because that is where nearly every class on the site lives and an implicit dependency that large is worth writing down. A utility used for the first time in a template is emitted by the build that renders it.

`hugo_stats.json` (auto-generated by Hugo's build stats, listed in `[build.cachebusters]`) is sourced separately only because Tailwind respects `.gitignore` and that file is ignored. It lists the classes an _earlier_ build rendered, which is what covers class names assembled at build time.

That distinction is the whole rule, and it replaces a "two-build lag" this file used to assert everywhere as the reason nearly all component styling was hand-written CSS. **The lag was real only for class names that never exist as literal strings.** Verified rather than assumed: `mix-blend-soft-light` and `isolate` appear only in `partials/grain-effect.html`, which nothing calls, so they can never reach `hugo_stats.json` — and both are in the built stylesheet.

So there is exactly one thing a scanner cannot see, and it has an answer:

- **A name built by concatenation** — `badge-{{ $color }}`, `alert-{{ $type }}`. Both families are safelisted with `@source inline(...)` at the top of `main.css`; keep those lists in step with the map in `chip-color.html`. `post-status-color.html` used to be a third caller of that safelist and is not any more: it returns whole literal class strings now, which is why the `text-{primary,…}` line that existed only for `post-status-legend.html` is gone. Where a template picks between literals instead — the `mark` shortcode's `text-accent`/`text-primary` map, the favorites pages' `aspect-square`/`aspect-[2/3]` — no safelist is needed, and that is the shape to prefer.

**One cascade trap replaces the old layer trap.** With everything in `@layer utilities`, two utilities that set the same property are decided by the order Tailwind emits them, not by the order they appear in a `class` attribute. It bites `display`: `hidden` wins over `block`, `contents`, `flex` and `grid`, and _loses_ to `inline-block` and `inline-flex`. Anything that starts hidden and is revealed by JS must therefore avoid the inline pair — `mastodon-toots.html` uses `block w-fit` for exactly this reason. Base vs. variant is safe in the usual Tailwind way (`sm:` always wins over unprefixed).

### Styling: utilities in the markup, not classes in `main.css`

**Style with Tailwind utilities in the template. Do not add a custom class.** `main.css` went from 1712 lines to ~600 in 2026-09 by moving every component block into the markup, and the reason those blocks existed — a "two-build lag" that made new utilities unsafe — was never true (see **CSS Pipeline** above). Adding a `.thing__part` back would re-create a problem the site no longer has, and it would be the only one of its kind left.

`main.css` is now allowed to hold exactly five things. Anything else belongs in a `class` attribute:

1. **Tokens and config** — the `@plugin "daisyui/theme"` blocks, the `html[data-theme=…]` hues, `@theme`, `@source`.
2. **Selectors for markup we do not write** — Hugo's `.TableOfContents` (`.toc a`), `@tailwindcss/typography`'s output (`.prose h2`, `.prose pre`), Pagefind's widget, element defaults in `@layer base`.
3. **Selectors no class can express** — the external-link `a[href^="http"]…::after`. Structural sibling rules used to belong here too, for the polaroid group's `nth-child` lean; with that gone, reach for an arbitrary variant (`[&_figure]:my-0`, as `image-row` does) before writing one back.
4. **`@utility` definitions**, for a recipe genuinely repeated across templates — `badge-tint`, `link-dash`. Three or more call sites, and only when nothing else competes for the same properties; two call sites is a copy-paste, not an abstraction.
5. **Nothing else.** A class used once is a utility string in the one template that uses it.

Before reaching for CSS, these cover almost everything that looks like it needs a rule:

- **Arbitrary values** for anything off the scale: `aspect-[16/10]`, `gap-[0.35rem]`, `text-[0.8125rem]/[1.5]`, `grid-cols-[repeat(auto-fill,minmax(8.5rem,1fr))]`, `w-[calc(100%_+_0.2em)]` (underscores become spaces; `calc` still needs them around `+`).
- **Arbitrary properties** for a declaration with no utility, custom properties included: `[stroke-width:0.09em]`, `[vector-effect:non-scaling-stroke]`, and a custom property declared then read back with `bg-(--some-token)`.
- **Arbitrary variants** for a descendant or pseudo-element you cannot reach: `[&_p]:m-0`, `[&_p+p]:mt-[0.6rem]`, `[&::-webkit-details-marker]:hidden`, `before:content-['·']`. **Never a `>` inside one**, and this is the one place the old "two-build lag" is real. Tailwind's source scanner reads a `.html` file as markup and ends the candidate at the first `>`, so `[&>figure]:my-0` is dropped from the build that renders it — no error, no rule. It then reappears on the _next_ build via `hugo_stats.json`, so it looks fixed locally and ships broken. Use the descendant form (`[&_figure]`); every arbitrary variant on the site does. Measured while building `image-row` in 2026-09.
- **`group`** instead of a descendant hover rule — `group` on the anchor, `group-hover:underline` on the title. Two rules about it, both learned the hard way: put it on the element that is actually a link (an unlinked row must not underline itself on hover), and **name it (`group/section`) whenever another `group` is nested inside**, because a bare `group-hover:` matches _any_ `.group` ancestor.
- **`data-*` attributes as JS hooks**, never classes. A utility is a poor hook: renaming a colour would silently break a `querySelector`. See `mastodon-toots.html`.

Two things to keep doing while you convert:

- **Move the rationale, don't drop it.** A rule's comment becomes a `{{/* … */}}` comment above the markup it now explains. The measured contrast ratios, the cascade traps and the "we tried X and it did Y" notes are the expensive part of this file; the declarations are not.
- **Verify structurally, not by eye.** Build to a scratch dir before and after (`hugo -d <tmpdir>`, twice — a running dev server owns `public/`), then diff the _element skeleton_ of every page, tags only, attributes stripped. The class churn makes a raw HTML diff useless, and the skeleton diff is what caught a partial being swapped into the wrong template during the 2026-09 conversion.

### Theming

Two DaisyUI themes: **sunrise** (light default) and **midnight** (dark). The active theme is stored in `localStorage` and applied before first paint via an inline script in `head.html` to prevent flash. `theme-toggle-script.html` handles the toggle UI logic.

**The palette is monochrome, from [Odin's Crow](https://www.awwwards.com/sites/odins-crow) — `#000`, `#9C9C9C`, `#ffffff` and nothing else**, adopted 2026-09. The three are used at full strength where they fit (white is sunrise's column and midnight's ink, black the reverse) and the rest of each ramp is plain sRGB greys between them, because the palette publishes three swatches and a site needs a ramp. The sourcing rule is unchanged: every value is looked up, never picked by eye, and carries its derivation in a trailing comment.

**`#9C9C9C` is a light-theme surface and a dark-theme ink, and that asymmetry is the palette's own.** It measures **2.75:1 on white** — so in sunrise it can only be a divider or a fill, never text — and **7.65:1 on black**, which is why it is midnight's `secondary`, the muted-caption slot. Do not reach for it as sunrise text.

**One accent survives, and it is the Truffle Trouble / Burning Flame pair** the previous MP072 palette left behind — sunrise takes the dark member (`#a35139`, 5.08:1), midnight the light one (`#ffb162`, 10.54:1), which is the inverse-brightness rule already. It is spent on exactly four things: **links** (`--color-accent` drives the site-wide dashed underline and `link-dash`), **the nav's active state**, **the post-status ramp** and **the rail accent** — the places where losing colour would cost navigation rather than only decoration. `primary` and `accent` are the same value on purpose; with one accent there is nothing for them to disagree about.

**Everything else is grey, including every chip.** `secondary`, `info`, `success` and `warning` are four greys of stepped weight and are now the whole chip palette; `error` is a fifth, still reserved for `disclaimerType` severity. Be honest about what that can carry: four greys are four levels, and as `badge-tint` fills (12% into `base-200`) the inner two are nearly indistinguishable. The chip's own label does the disambiguating now, and the solid-vs-tinted split is what still separates categories from tags. `chip-color.html` was moved off `primary`/`accent` for this reason, and so were the callers' defaults for an unmapped term — an unmapped tag or category used to fall back to `"accent"`/`"primary"`, which would have rendered the one accent colour on an arbitrary chip.

**The four alert severities differ by tone and icon, not hue.** `icons/alert/` already ships a distinct glyph per severity, and the four tokens step in weight, so an `error` alert still reads as heavier than an `info` one. This is a real reduction in signal and it was chosen deliberately over spending the accent on `error`, which would have made a link and a failure the same colour.

**Midnight's dark ramp is written as plain sRGB greys, not OKLab mixes, and that is not a style choice.** OKLab lightness compresses hard near black: a 9% grey-into-black mix computes to `#010101`, putting the column-to-ground step at **1.006:1** — an invisible ramp. Mixing works at sunrise's end of the scale and not at all at this one.

**The fill tier survives the monochrome switch**, and it is where the loud values live that can never be text:

- **Tokens are ink.** Everything in the two `@plugin "daisyui/theme"` blocks is text-safe on `base-200`, which is what confines sunrise to the palette's dark members plus Tailwind's 700/800 band, and midnight to Tailwind's 400 band.
- **The loud colours are literals in the markup** — `text-[#ffb162]` on the post card's plate, `bg-[#ffb162]/15` in `empty-state.html`. They are never tokens, never theme-switched, and **never text on a base surface**. Three consequences worth knowing: they need no `@theme` entry, no `html[data-theme=…]` override, and — because they exist as literal strings in the markup — no `@source inline(...)` safelist either (verified: all three appeared in the stylesheet on the build that first rendered them). And they are deliberately the same colour in both themes, because a poster block is the same yellow either way, with ink on it regardless.

Do not "fix" a fill-tier utility into a token. The reason it is not one is that it fails as text, and promoting it would silently put it somewhere it fails.

**The blog post status chips are the second fill-tier family, and they are one warm ramp declared in a plain `:root`.** `--status-{seed,growing,living}-{start,deep,ink}` sit next to `--rail-*` in `main.css` for the same reason those do: they do not vary by theme, so neither `html[data-theme=…]` block needs a line, and `@theme` is wrong because Tailwind v4 prunes theme variables no generated utility references (these are only ever read through `var()` from the class strings `post-status-color.html` returns). Four things make this the shape it is:

- **One hue at three lightnesses, because the statuses are one axis.** 🌱 seed / 🌿 growing / 🪴 living is a plant maturing, and it used to be spent on three unrelated brand tokens, which read as three categories rather than three steps of one. That hue is the site's single accent — the Truffle/Burning Flame family — because on a monochrome page the status is one of the few things worth spending colour on. It was an emerald ramp until the palette went black-and-white.
- **The bands straddle the hole in the middle of the family, and that is what fixes them.** Full Truffle measures 3.53:1 under the dark ink and the mid step 3.02:1 under the pale one, so no band is allowed to contain that crossover. Measured ink-on-fill at _both_ ends: worst pair is living's light end at 5.18:1, the rest run 6.06–15.20. Seed and growing take the deep warm ink, living the pale one — exactly the shape the emerald ramp had around its own 600 hole.
- **A status chip is a fill, never text on a page surface**, and here that is a proof rather than a preference: no single step clears 4.5:1 on both grounds at once, because sunrise's white ground and midnight's near-black one pull the requirement in opposite directions. That is what turned `post-status-legend.html`'s coloured labels into chips — it now renders the chip a post actually carries.
- **Contrast against the ground is not the measure here.** Seed's pale fill is quiet against sunrise's white and loud against midnight's black; living's deep fill is the reverse. A chip fixed across both themes is necessarily quiet against one of them, and what defines it is its ink — every chip's own text clears 5:1 — rather than its edge.

The two blocks are kept deliberately in step — they drifted apart once and had to be reconciled. Four rules hold them together; breaking any one of them is what caused the drift:

- **Shape tokens are identical in both themes.** `--radius-selector`, `--radius-field`, `--radius-box`, `--size-*`, `--border`, `--depth` and `--noise` are copied verbatim between the two blocks. Only the colours differ. If you change a radius, change it in both.

**The site has no radius: all three daisyUI radius tokens are `0`.** daisyUI splits them by component family — `--radius-selector` for badges and toggles, `--radius-field` for buttons and inputs, `--radius-box` for cards, alerts and modals — and they were `1rem`/`2rem`/`0.25rem` until 2026-08, which gave a chip, a button and a card three different corners; they were then held equal at `0.75rem` until 2026-09, when the site went square. Holding all three at the same value is still the whole mechanism — every daisyUI component, the `.prose pre`/`kbd` override and Pagefind read from these — so a corner comes back site-wide by changing three numbers in each theme block, and nowhere else. Four things sit outside the tokens and have to be kept in step by hand:

- **Hand-written panels declare nothing, and that is now the whole story.** The post card and `.favorites-card` are not daisyUI components, so nothing rounds them for free; they used to carry `rounded-box` in their templates (`post-card.html`, `favorites/single.html`) and no longer do. If a radius ever returns, the utility goes back in the markup, which is now where the whole of both lives anyway — and on the post card it goes on the frame only: the plate is flush to three of its edges, so a corner there is the frame's to draw, not the plate's.
- **Nested boxes no longer need a stepped radius, and the `--radius-inset` that did it is gone.** Worth knowing why it existed, because it comes back with any radius: two nested boxes carrying the same `border-radius` are not concentric — the panel's corner curves from its own outer edge, so 9px in (`padding: 0.5rem` plus the 1px border) only a 3px corner is left, and a 12px cover corner inside that widens the frame from 9px along the straight edges to 12.7px across the diagonal. That gap is what reads as "the corners don't match". The fix was `--radius-inset: max(0px, calc(var(--radius-box) - 0.5rem - 1px))` on each panel, read by the post-card cover and the favorites card's cover and placeholder. At `--radius-box: 0` it computed to `0` for everyone, so it was removed rather than left as arithmetic that always returns zero.
- **Pagefind is overridden through its own variable**, in the unlayered `html:root` block at the very bottom of `main.css`. `pagefind-component-ui.css` declares `--pf-border-radius: 6px` on a plain unlayered `:root`, so a layered rule of ours loses outright and a matching `:root` would be decided by stylesheet order; `html:root` (0,1,1) settles both, the same trick as the `html[data-theme=…]` blocks. **These cannot live in `@theme`** — Tailwind v4 prunes theme variables no generated utility references, and nothing references `--pf-*`, so the `--pf-font` that sat there for a long time never actually reached Pagefind.
- **Circles are exempt.** The toot profile avatar stays `rounded-full`; an avatar reads as a person.
- **No `rounded-*` utility appears anywhere in `layouts/`, and none should.** Every value on Tailwind's scale is a literal, so one would put back a corner that no token can switch off again; `rounded-none` is equally unnecessary, since the tokens already resolve to `0`. `rounded-box` is the only one that maps to the token and is therefore the only one to reach for if a radius returns. Where no single utility fits — there is no `rounded-t-box` — let a parent's shape clip the child with `overflow-hidden`, which is what `now-top-artists.html` still does.
- **Every brand/semantic colour pairs a colour with its inverse-brightness `-content`.** In sunrise the colour is the _dark_ member and `-content` is the paper (`base-100`); in midnight the colour is the _light_ member and `-content` is near-black (`stone-950`). This is what lets one token work both as `text-primary` on the page and as a `badge-primary` background — the two demands pull in opposite directions, and only this split satisfies both.
- **Contrast is measured against `base-200`, not `base-100`.** `<html>` carries `bg-base-200` and cards sit on it, so it is the worst-case surface. Every colour clears 4.5:1 there.
- **`base-300` is the only divider token, and `neutral` is never one — nor a chip.** `neutral` is a dark surface in midnight but near-black text in sunrise, so a hairline mixed from it (`border-neutral/10`) reads in one theme and vanishes in the other. `base-300` is a surface step in both. The same asymmetry rules `neutral` out of `.badge-tint`: midnight's `neutral` is `olive-900` `#1d1d16`, within a hair of the `stone-900` `#1c1917` ground it would sit on, and measures **2.06:1** as a chip. It is excluded from the chip palette (see `chip-color.html`); an earlier version of this file implied all eight DaisyUI variants were chip-safe, which was never true of this one.

**The base ramp runs in opposite directions in the two themes.** In sunrise `base-100` is the _lightest_ step — the reading column is palette white; in midnight it is the _darkest_, palette black. `base-200` is the anchor in both cases because `<html>` carries `bg-base-200`, which is also why it is the surface contrast is measured against. Sunrise runs `#ffffff` → `#f5f5f5` → `#d0d0d0`, midnight `#000000` → `#111111` → `#303030`. Sunrise steps 1.090:1 column-to-ground and **1.415:1** for the divider; midnight 1.112:1 and 1.431:1 — the two ramps are near mirror images, which they were not under any previous palette.

**Both dividers are deliberately heavy** — about 1.42:1 against their ground, against the 1.187:1 whisper the site carried before 2026-09. `border-base-300` is the column's `border-x` in `baseof.html`, card borders, the `.toc` guide line, the favorites list's `li` hairlines and the post card's corner strip, so it is the one token that draws nearly every edge on the site; on a page with no colour it is also most of what gives the layout its structure.

`text-base-content/70` is the floor for muted text; `/50` and `/60` fall under 4.5:1 in one theme or the other. `.toc a` uses the same 70% via `color-mix`. Both inks are a palette colour at full strength — black in sunrise, white in midnight — so the 70% mix has more room than it has ever had: 12.99:1 and 8.61:1. That headroom is new, and it is worth not spending: `/50` and `/60` are still the wrong reach, because the floor exists so the value survives the next palette rather than because this one is tight.

**`.badge-tint` is the site's pastel chip fill**, replacing DaisyUI's `badge-outline` on every tag/label chip (the `#tag` links, the snippets language, the favorites "Reading" and `PT`/`EN` badges, the homepage favorites-category chip). The solid category chips keep their fill, which is what keeps categories reading above tags. It is written against `--badge-color` — DaisyUI's own per-badge token, set by `badge-accent` & friends — so one rule covers every colour variant, and an uncoloured chip falls through to `base-content`. Three things bite:

- **It is an `@utility`, which is what makes it win.** DaisyUI compiles `.badge` into `@layer utilities` and sets `background-color` there, so a `@layer components` rule would lose to it regardless of specificity. `@utility badge-tint` registers with Tailwind and is emitted into the utilities layer _after_ daisyUI's nested `@layer daisyui.*` sub-layers, so it overrides the fill by construction. (It was an unlayered hand-written rule until 2026-09, for the same fight.)
- **The fill alone would break contrast; the text mix is what saves it.** Sunrise's `primary` clears 4.5:1 on `base-200` by only 0.08, so _any_ fill behind pure-token text drops it under. `.badge-tint` pulls the text 30% toward `base-content`, which fixes both themes with one declaration precisely because of the inverse-brightness pairing above — near-black in sunrise, light in midnight, so it pushes text away from the fill in whichever direction that theme needs. **Worst case across all six chip hues × both themes is 5.39:1** (sunrise `primary`); every other hue sits between there and 9.21. Sunrise is what pins the fill.

  These numbers were re-measured in 2026-08, in 2026-09 when the palette dropped to daisyUI's own six, and again in 2026-09 when it moved onto Tailwind's scale. Re-measure after any palette change: the worst chip moved 5.57 → 5.86 → 5.39 across the last three, so the fill's headroom is not a constant. Re-measure before leaning on that headroom — the method is OKLab `color-mix` exactly as the CSS does it, checked against WCAG reference pairs and against the shipped `-content` values, which it reproduces bit-exactly.

- **Hover steps the border, never the fill.** Raising the fill on hover dropped midnight to 4.12–4.24 in every variant on its old, lighter ground; the darker rebuild bought that margin back, but the rule stays because sunrise still has none. Both border colours are always-on values on a border that is already 2px (`--border`), so nothing reflows.

**The chip palette is daisyUI's own six, and `layouts/partials/chip-color.html` is the only place a chip's colour is decided.** DaisyUI ships eight variants, but `neutral` is unusable as a chip (above) and `error` is reserved for `disclaimerType` severity, leaving **`primary`, `secondary`, `accent`, `info`, `success`, `warning`**. Four hand-written hues — `orange` (50°), `sea` (161°), `azure` (226°), `rose` (345°) — sat alongside them from 2026-08 until they were dropped in 2026-09, taking their `html[data-theme=…]` token blocks, their four `@utility badge-*` definitions and their safelist entries with them. Three things to know:

- **A hue is a theme token now, so there is no such thing as adding one cheaply.** Each hand-written hue cost a `--color-x` / `--color-x-content` pair in _both_ `html[data-theme=…]` blocks, a `@utility badge-x` setting `--badge-color` + `--badge-fg` (the two declarations daisyUI's own `badge-primary` compiles to, which is what gave both chip shapes for free), and a name in the `@source inline(...)` safelist. Wanting a seventh chip colour means paying all of that again and re-measuring it against `base-200` in both themes — not editing a map.
- **The six are still safelisted**, along with the two variants no chip uses. Every call site builds its class as `badge-{{ $color }}`, so no scanner ever sees a hue as a literal string; the safelist is what keeps them in the stylesheet.
- **Recolouring a chip is a map entry, not a template edit.** `chip-color.html` takes `(dict "family" … "key" …)` — families are `lang`, `category`, `tag` — and returns a colour keyword or `""`. Every caller keeps its own default for `""`, so an unmapped tag is never unstyled, just uncoloured. Tags are grouped by topic on purpose (`java`/`oop`/`programming` share a hue) so a post's tag row reads as a set rather than a rainbow, and with six hues covering three families that sharing is now the rule rather than the exception: the six tag groups take one hue each, and only the three blog categories never share. (A `favorites` family mapped the collections by what the thing _is_ until 2026-09; its only reader was the homepage's "recently added" row, and it went with that row.) The chip's own label is what disambiguates.

Blog category chips stay **solid** while tags stay tinted. That contrast is now the _only_ thing keeping categories reading above tags, since both families carry colour — don't tint the categories. **Two surfaces name the category instead of chipping it**, and both put a letterspaced kicker over a `text-primary` name: the post card (originally because its ink plate could not carry a brand colour, now by preference — see **Post Cards**) and a post's own footer box (see **Post Footer**). The rule they share is that a chip's job is to pick one item out of a row of many, and on both of those the category is a single labelled field. Chips remain everywhere a category appears among others — /blog's category row, the term pages.

### Layout Hierarchy

```
layouts/_default/baseof.html        ← shell: sidebar + main slot + PhotoSwipe scripts
  └── layouts/index.html            ← homepage
  └── layouts/<section>/list.html   ← section index pages
  └── layouts/<section>/single.html ← individual pages
  └── layouts/_default/single.html  ← fallback single
  └── layouts/_default/list.html    ← fallback list
```

All layouts use `{{ define "main" }}` blocks. Chrome is split by viewport: `rail-left.html` and `rail-right.html` are the desktop rails (`hidden lg:…` on each rail), and `mobile-topbar.html` + `sidebar-mobile-drawer.html` take over below it.

**The shell is three grid tracks from `lg` up and a plain block below it**, written as utilities in `baseof.html`: `lg:grid` plus one of two `lg:grid-cols-[…]` literals, picked by `has-toc.html`. **The nav rail is the wider of the two — 15rem at `lg`, 17rem at `xl`, against the tools rail's 13/15.** Both were 13/15 until 2026-09; the nav rail carries the title, menu, search box, social row, webring and footer meta where the tools rail carries two buttons and a TOC, so the extra 2rem goes where the content is. The rails are therefore no longer equal, and the capped column in the middle sits 1rem right of the viewport centre on a TOC page — deliberate, and small, since it is the middle _track_ that shifts and not the `max-w-4xl` measure, but it is the reason the two used to match. Restore both to one value if the drift ever reads wrong. A page with no TOC narrows the right track to `5rem` — the width of a column of `btn-sm btn-square` buttons plus the rail's `1.25rem` padding and slack for focus rings — so those pages were never symmetric anyway; now that both rails are painted, that asymmetry is visible rather than merely structural. The widening spends middle-track width at every viewport and bites hardest at exactly `lg`, where 64rem less 15rem less 13rem leaves a 36rem middle: the reading column loses 2rem there, and stops caring once the middle passes the 56rem cap. Tailwind's `lg`/`xl` are 64rem/80rem, exactly where the hand-written media queries used to sit. The rails carry their own sticky sizing (`lg:sticky lg:top-0 lg:self-start lg:max-h-screen lg:overflow-y-auto`), written out in both files rather than shared: it is eight utilities and the two rails differ, since the left one is a flex column so its footer block can be pushed down with `mt-auto`.

**Both rails are dark chrome in both themes, and they get there by rebinding tokens rather than by re-colouring children.** `rail-chrome` (an `@utility` in `main.css`) paints the rail from `--rail-bg` and then reassigns `--color-base-content`, `--color-heading`, `--color-base-200/300` and **every** semantic slot for the whole subtree; custom properties inherit, so the nearest ancestor that sets one wins and every descendant re-inks by construction — including daisyUI's bare `.btn`, which reads `--btn-bg` from `--color-base-200` and `--btn-fg` from `--color-base-content`.

**Rebinding the variables is not enough on its own, and this bit is easy to get wrong.** daisyUI declares `color: var(--color-base-content)` on `:root,[data-theme]`, which resolves _at the root_ — so what inherits into the rail is the page's ink as a computed value, no matter how many variables the subtree rebinds. Everything that relies on inheritance rather than naming a token keeps it: the social icons (`fill="currentColor"`), the webring anchors, any bare text. `rail-chrome` therefore re-declares `color: var(--rail-ink)` itself. Without that line they render black-on-near-black in sunrise.

**All six semantic slots collapse to `--rail-accent`, including `info`/`success`/`warning`/`error`.** Chrome has no semantic states to signal — a nav rail is never "success" — and leaving them bound to the page palette is what once put an `indigo-700` moon on a slate rail: `icons/moon.html` carries `text-info` and `icons/sun.html` `text-warning`. Only one of those two is ever visible, since the theme script hides the other, so the warm/cool pairing they were built for is never actually seen and one accent costs nothing. Each rail file chooses only its hue: `[--rail-bg:var(--rail-nav)]` on the left, `[--rail-bg:var(--rail-tools)]` on the right. **The `--rail-*` values are declared once, in a plain `:root` block, because the chrome does not vary by theme.** `#1c1c1c` (nav) and `#242424` (tools) are the rails in _both_ themes, with white ink and the Burning Flame accent on top. Those two near-blacks sit _below_ every surface sunrise has and _above_ every surface midnight has, so one set of values reads as sunken chrome in the light theme and raised chrome in the dark one. Every ratio inside a rail is therefore literally the same number in both — ink 17.04:1 and 15.52:1, accent 9.51 and 8.66, muted `/70` 8.13 and 7.74.

A plain `:root` rather than the `html[data-theme=…]` blocks: nothing competes for these, so the specificity trick those need does not apply. **Not `@theme`** — Tailwind v4 prunes theme variables no generated utility references, and these are only ever read through `var()` inside `rail-chrome`, which is exactly how the old `--pf-font` silently never reached Pagefind.

**The nav rail is the darker and more strongly separated of the two.** Against sunrise's white column it measures 17.04:1; against midnight's black one, 1.23:1. That gap is a property of dark themes rather than a shortfall: WCAG ratios compress at the dark end, where the formula's `+0.05` offset dominates. Midnight's column is now pure black, so this is the ceiling by construction — nothing can separate from it further and still be a dark surface. Perceptually the step reads; the number is just the wrong instrument down there.

**`nav-link`'s inactive state is `/70`, not the `/60` it carried until 2026-09.** `/70` is the site-wide floor for muted text and `/60` was always beneath it; the shortfall simply never showed on a near-black rail. It is independent of the rails anyway: on sunrise's **mobile drawer**, where the background is `base-200`, `/60` measures 4.33:1 and fails outright, while `/70` gives 5.77. Do not put it back.

Three things follow. **Painting them was not optional once the palette landed**: sunrise's `base-content` is black and the rails are near-black, so a painted rail with un-rebound tokens renders its own menu invisible. **`rail-right.html` cannot drop `lg:min-h-screen`** — `self-start` stops the rail stretching, so without a floor a page with a short TOC paints a stub of chrome a few hundred pixels tall instead of a full-height column; the left rail already had it. And **Pagefind is rebound the same way**: its widget hardcodes a white field (`--pf-background: #fff`) on a plain unlayered `:root`, which inheritance settles without a specificity fight. That also re-skins its results dropdown, which is anchored to the rail and reads as part of it.

**One trap this uncovered, and it corrects an assumption elsewhere in this file.** Lightning CSS's synthesised `color-mix` fallback — the one `badge-tint` documents — is **dead code when the target is a custom property**. For `badge-tint` it emits an `@supports` guard, which works; for `rail-chrome` it emits the un-mixed value as a plain preceding declaration of equal specificity, and an unregistered custom property accepts any token stream at parse time, so the `color-mix` declaration always wins even where it cannot be computed. The failure surfaces only at substitution, where the _using_ declaration becomes invalid at computed-value time and falls back to that property's initial value — never to the earlier declaration. So: real fallback for ordinary properties, illusory for custom ones. `rail-chrome` is left unguarded anyway (as `.toc a` already is), because `--rail-bg` is never mixed and so the rails still paint; only the raised surfaces and hairlines drop out.

**Every page is capped at `max-w-4xl` (56rem / 896px) by a single wrapper inside `<main>` in `baseof.html`** — one measure for the whole site, sitting inside the padding rather than on `<main>` itself. `wide: true` in a page's front matter drops the cap so a grid or gallery can use the full centre rail; **nothing uses it today.** `content/<lang>/library.md` was the one caller until /favorites broke that page into one page per collection: a single collection's poster grid runs six across at `max-w-4xl` and the list-shaped ones are rows of text, so neither needs the rail back. It is a page param, so a section list page needs it in its `_index.md`.

The cap was `max-w-prose` until 2026-08 — 65ch, which at the site's 16px root worked out to ~637px. It was widened to match a reference layout whose text column measures 915px; `max-w-4xl` is the nearest step on Tailwind's container scale (`max-w-5xl` is 1024px, `max-w-3xl` 768px). Two things follow. **The root font-size is 16px, the browser default** — the old shell CSS carried a comment claiming 18px was set on `html`, and nothing in the repo ever set it; don't size anything off that claim. And **896px at a 16px body is roughly 90 characters a line**, past the usual 65–75 band (the figure was measured under the previous body face; Inter sets a little wider, so the real count is somewhat lower): that reference layout buys its width with a 20px body font, which this site does not have. The step down if it reads too long is `max-w-3xl` (~78ch), not a return to `max-w-prose`.

**Body copy runs at `line-height: 1.7`**, set on `.prose` in the unlayered block at the bottom of `main.css` beside `--tw-prose-headings` (@tailwindcss/typography's own default is 1.75). It sits on the wrapper, not on `.prose p`: the plugin gives paragraphs no line-height of their own, so the value reaches them — and list items, blockquotes and definition lists — purely by inheritance, and pinning only `p` would put a visible step between a paragraph and the list under it. Unlayered is load-bearing here for a second reason beyond the usual one: `prose-base`, the size modifier `_default/single.html` carries, re-declares 1.75 as its own (0,1,0) utility.

### Post Cards

**`layouts/partials/post-card.html` is the only place a blog post's card shape is decided.** Three surfaces call it — `blog/list.html` (the "Latest" card and the archive grid), `index.html` (the homepage row) and `_default/taxonomy.html` (tag and category term pages) — so the same reasoning as `blog-posts.html` owning the ordering: one partial owns the shape, and the three cannot drift. Posts rendered in five different shapes before 2026-08, only one of which showed a cover.

**The shape**: a 16:9 cover running edge to edge, a flush two-chip strip overlapping its top-left corner, and a padded text block beneath it carrying a category kicker, the title, a rule and the meta line. **The card is the favorites' panel recipe** — `bg-base-200` inside a `border-base-300` hairline with a shadow, the same string `favorites/single.html` uses — and the two are deliberately kept in step: cover art is an object and a surface under it says so, and the site's two card families should not disagree about what a card is made of.

It was an opaque `neutral` **ink plate** between 2026-09 and the palette work later that month. That is worth knowing because it is the only reason the category is a letterspaced kicker rather than the solid chip it is everywhere else: nothing coloured could sit on a surface that dark. On `base-200` the constraint is gone and the kicker is now a preference, not a requirement.

Signature is `(dict "page" $post "featured" <bool>)`. `featured` is the full-width variant used once per `/blog`. **Callers own the grid, the partial owns the card** — `blog/list.html` and `_default/taxonomy.html` use `grid grid-cols-1 sm:grid-cols-2 gap-4` (~430px a card inside the cap), `index.html` uses `sm:grid-cols-3` (~240px). Ten things bite:

- **`$post` must be captured before `{{ with .Params.cover }}`.** Covers are page-bundle resources (bare filenames), so `responsive-image.html` needs `"page" $post` to resolve them — but inside the `with`, `.` is the cover _string_.
- **The text block declares no background of its own** — the card's `bg-base-200` shows through — so there is one surface to keep in step rather than two. `neutral` is no longer used anywhere in `layouts/`: the exclusions on it elsewhere (never a divider, never a chip) stand unchanged, and it now has no exception.
- **The card's colours are ordinary base tokens again.** The kicker is `text-primary` (4.58:1 sunrise, 10.42:1 midnight), the title takes `link-dash` and the heading colour from `@layer base`, and the excerpt and meta row sit at `base-content/70` (5.77 / 7.23) over a `border-base-300` rule. On the ink plate none of that was possible — every brand token measured about 2:1 there, so the kicker had to be the fill-tier Burning Flame literal and `link-dash` had to be respelled as `neutral-content` longhands. Categories still render as **solid** chips everywhere else — /blog's category row, the term pages — which is what keeps them reading above the tinted tag chips.
- **The corner strip is one flex row, not two pinned chips.** Language first (uncoloured: `bg-base-100`, `font-mono`, the `post_lang_written_in` title), then the status, solid in its own colour. Two separately-positioned chips do not line up — whichever one is wrapped in a positioning element sits inside a line box and gets nudged down by baseline alignment, while a chip that _is_ the positioned element starts flush at the offset. One row makes the alignment structural. `post-lang-badge.html` was folded into this strip and deleted; the favorites pages keep their own `favorites-item-lang-badge.html`. The blog feed mixes both languages (`blog-posts.html`), so every card is badged rather than only the foreign ones.
- **The status is a gradient chip on the cover, and its colours are the warm accent ramp, not theme tokens.** It sat muted in the meta row until 2026-09, on the grounds that a coloured chip is loud beside two muted meta items — which is still true, and is why moving the chip 400px away onto the cover is what let it be coloured. `post-status-color.html` stays the only place the colour is decided; it returns a dict of **literal class strings** — `ramp` for this card's two-stop gradient and `chip` for the flat badge elsewhere — so the two shapes are the same colour by construction, and neither needs an `@source inline(...)` entry. Every stop reads a `--status-*` variable from the plain `:root` block in `main.css` (see **Theming**), so a status is the same warm step in both themes. An archived or unset status falls through to the paper ramp, `base-100` → `base-200`, which is the one entry that is still theme-aware. Each chip ramps _within its own band_ — the previous version mixed its second stop 25% toward `base-content`, which was right while the colour came from the tokens and is exactly the part that had to go: it would have left one stop of a fixed chip still flipping by theme. Both ends of every band are measured against that band's own ink, so the gradient cannot walk a chip out of contrast. The `| default ""` dance the old keyword lookup needed is gone with it — the partial returns a dict for every input, archived included. `post-status-emoji.html` and `post-status-icon.html` are untouched and still used by `page-list.html`, `post-footer.html` and `post-status-badge.html`.
- **The meta row is date `/` reading time only, with no icons.** `icons/meta/calendar.html` and `icons/meta/clock.html` were the card's only callers and were deleted with it: a 14px glyph beside letterspaced 11px capitals reads as a bullet, not as an icon. The third icon convention is gone with them — two remain, the root-level icons and `icons/alert/`. In pt-br this row is still the tightest fit in the design (`19 DE JUN. DE 2026 / 8 MIN DE LEITURA`), which is what `flex-wrap` is for, and why the micro-type is 11px rather than the mockup's 10px.
- **The plate sits _under_ the cover, not over it, and that is the one place this departs from the mockup.** There the plate is an overlay, which works because the frame is 3:4 — enough height to give a plate ~130px and still show most of the photo. A 16:9 frame has no such room, and the numbers are worth keeping because they are what settles it: measured on /blog, a 367px archive card is 206px tall against a plate that needs 134px, leaving a 70px band of cover, and the homepage's three-up row is narrower still. **A 16:9 cover and an overlaid plate are not both possible at these widths.** So the cover keeps its full ratio, the plate is stacked beneath it, and the card's height is content-driven — no `aspect-ratio` on the card itself, nothing that can clip, and no floor to keep in step with the plate. Only the corner strip still overlaps. If the overlay is ever wanted back, the frame has to get taller first.
- **The cover box is `aspect-[16/9]` in both variants, and it is always rendered, cover or not.** It is the corner strip's surface: every post carries a cover today, but `archetypes/blog.md` emits `cover: ""`, and without the box the strip would land on the kicker. `bg-base-200` sits on the card itself, not just the text block, so a coverless post gets an empty panel band above its text rather than a hole. Featured differs from the grid card only in padding, a larger title, the excerpt (there is horizontal room for it and none on a grid card) and the `blog_keep_reading` line. The title clamps to two lines in both, which is also what keeps a row of grid cards near-uniform in height.
- **The cover is static.** No hover scale, no fade, no transition on it — the title's dashed underline is the card's only hover cue, and `group` on the anchor is what carries it.
- **The branching class strings are `cond` variables interpolated whole.** `$platePad`, `$titleSize` and the shared `$micro` are built above the markup rather than written as inline `if` actions inside a `class` attribute — prettier-plugin-go-template drops whitespace written inside an action body and silently glues two class names together. See **Formatting**.

The whole card is utilities in the partial. The covers stay in colour: the mockup greyscales them, but that is a treatment its design system applies to every image, and here it would put a card's cover and the same photo on the post's own page in two different worlds.

`layouts/partials/page-list.html` survives as `_default/list.html`'s renderer and is deliberately _not_ card-shaped: it serves sections with no cover art. `dated-list-item.html` was the /blog archive row and was deleted when the grid replaced it.

**The homepage has no favorites row.** A "Recently Added" list sat under "Recent Posts" until 2026-09, built from every dated entry across `data/favorites/`. It went when the dates did: games, albums and TV are hand-ordered lists now, and a newest-first row over the one dated entry left would have been a row of one. `home_recently_added`, `home_browse_favorites` and the `favorites` family in `chip-color.html` were its only dependants and are gone with it. The row and "Recent Posts" had once been deliberately identical markup; that pairing had already been broken when posts got cards.

### Post Footer

**`layouts/partials/post-footer.html` owns the whole trailing area of a blog post**: a taxonomy row on top (a `Categories` kicker beside a `Tags` kicker) and a prev/next row beneath it, separated by one rule. `layouts/blog/single.html` calls it once, immediately after `</article>` and before the comments section.

It replaced five loose siblings — an `<hr>`, a folder-icon category row, a tag-icon tag row, the comments and a separate `prev-next-nav.html` — each drawing its own edge at its own weight and none of them lining up. `prev-next-nav.html` was folded in and deleted; it had no other caller, which is what let `nav_previous`/`nav_next` drop the `←`/`→` from their i18n strings. `icons/folder.html` and `icons/tag.html` went with the icon rows, on the same reasoning that removed the card's calendar and clock: a glyph beside a letterspaced 11px label reads as a bullet, not as an icon. **Only the root-level icons and `icons/alert/` remain**, and both those directories are now one file smaller.

**There is exactly one border, and it is the site's ordinary hairline: `border-t border-base-300`** — 1px, the same edge the post card, the favorites card and the favorites list's `li` rows all draw, and the same one the comments section below now carries, so the page ends with two rules of one weight. It was a full `border-4` box for a day in 2026-09, the shape of the mockup it came from, and both the frame and the weight went: nothing else on the site draws a box, and 4px is the _image frame's_ weight — every `border-4` left in `layouts/` is `border-base-200` around a photo, never a rule. Rules are the `base-300` hairline. The two rows do not need enclosing to read as a pair. Two things went with it and should not come back on their own. **The vertical divider between the neighbours**, because a rule floating between two cells with no box around them is an orphan — the columns are separated by `gap-x-8` now. And **the cells' horizontal padding**, because inset content lines up with the article above only while a border is there to inset it from; without one, `p-5` pushed the whole footer off the reading column's left edge. Vertical padding stays, as the gap either side of the rule.

Six things bite:

- **`data-pagefind-ignore` sits on the nav row only, never on the footer.** The category and tag links carry `data-pagefind-filter`, and Pagefind drops an ignored element from the index outright — the filters inside it included — so ignoring the whole footer silently empties the search facets. The neighbours' titles are the only part here that is another page's content, and they are what the attribute is there for.
- **The footer paints nothing when there is nothing to put in it.** Each row is guarded independently and the `<footer>` itself on the union, so an untagged, uncategorised post with no neighbours renders no element at all rather than a bare rule.
- **The rule belongs to the nav row and is unconditional.** With taxonomy above it, it separates the two rows; with none, it separates the footer from the post's own content. There is deliberately no rule above the taxonomy row — the `mt-10` is what sets it off from the article.
- **A lone neighbour takes the full width.** `sm:grid-cols-2` is applied only when both a previous and a next exist; one cell in a two-column grid would sit in a half-width column for no reason.
- **The neighbours come from `blog-posts.html`, not from `.PrevInSection`/`.NextInSection`.** Those two are _language-scoped_ — each language is its own Hugo site with its own `contentDir`, so they only ever walk `content/en/blog/` or `content/pt-br/blog/` — while /blog, the homepage and the RSS feed all read the merged feed. A reader browsing that mixed list would click into a post and silently land on a shorter chain: measured in 2026-09, **four of seven posts were dead ends in one direction** when only the two true ends of the merged list should be. The newest EN post offered no Next with a newer pt-br post sitting directly above it in the list it came from, and the oldest pt-br post offered no Previous with four older posts below it. The partial is newest-first and already drops the foreign copy of a translated post, so the neighbours are one index either side — a _lower_ index is newer, hence Next. This makes the footer the fourth surface reading that partial, which is the whole point of it owning the ordering: the nav cannot disagree with the list that led here. Pages are matched on `.Permalink`, which is unique across both sites by construction, rather than by page identity.
- **Both cells read left-to-right.** The old nav right-aligned "next", which put the two labels at opposite ends of a wide row with nothing between them. The label names the direction; the alignment does not have to.
- **The category is a kicker over a `text-primary` name, not a solid chip.** Same shape as the post card, for the reason given under **Theming**: a single labelled field is not a row to pick one item out of. Every category takes `text-primary` rather than the hue `chip-color.html` would give it — a `text-` class built by concatenation exists as a literal string nowhere and the safelist covers only the `badge-` and `alert-` families. The hue still reads on the tag chips one column over.

**`layouts/partials/post-neighbour.html` is one cell of that row**, extracted rather than written twice: the two cells differ only in their label, and the pair had already drifted once — the old nav right-aligned "next" and left-aligned "previous". **Every neighbour carries a language chip, not only the foreign ones**, which is the call `post-card.html` makes for the same reason: the nav walks the merged feed now, so a cell can hand an EN reader a pt-br post, and an unbadged cell would leave implicit what the list the reader came from states on every card. Badging only the foreign one is worse — it reads as a warning rather than a fact, and it makes the unbadged cell ambiguous. The chip is deliberately uncoloured (`badge-tint` with no `badge-<hue>` beside it falls through to `base-content`, as the card's corner strip does): a hue here would imply a category the cell does not have.

The micro-type is `post-card.html`'s string verbatim — `font-heading text-[0.6875rem]/[1.2] font-semibold uppercase tracking-[0.12em]`. All four labels here (`Categories`, `Tags`, `Previous`, `Next`) are the same kind of thing as that card's kicker, a word naming the field under it, so they are typed the same. It is copied rather than shared: two call sites is a copy-paste, not an abstraction.

### Nav Menu

`layouts/partials/nav-menu.html` is the only template that reads `Site.Menus`; it is called twice — from `rail-left.html` (`variant "desktop"`) and `sidebar-mobile-drawer.html` (`variant "mobile"`). The two variants differ only in padding and font weight, so the anchor itself lives in `layouts/partials/nav-link.html` and both variants (and both nesting levels) render through it.

Menu entries are configured in `hugo.toml` under `[[menus.main]]`, with one exception: the twelve children of Favorites are declared by the content adapter that builds those pages (see **Content Sections** below), because they are one per file in `data/favorites/` and hand-writing them would undo the point of that directory. Three things bite:

- **Labels come from `{{ i18n .Identifier }}` with no fallback** — a new entry needs a key in _both_ `i18n/en.toml` and `i18n/pt-br.toml`, or the link renders empty.
- **`.Params.icon` resolves to `layouts/partials/icons/nav/<icon>.html`** — or, when the name carries a slash, to any set under `icons/` (`favorites/albums`). A missing partial is a hard build failure either way. Every icon renders inside a `[&_svg]:w-4 [&_svg]:h-4` wrapper: the `favorites/` set carries no size of its own because it has two callers at two sizes, and the wrapper is a no-op on the nav set, which is already `w-4 h-4`.
- **`.Params.hidden` skips an entry entirely** (`projects`, `snippets`, `photos` use this).
- **A generated entry needs a matching identifier, not a matching label.** The Favorites children set `identifier` to the i18n key they already carry (`favorites_category_albums`), which is what satisfies the no-fallback rule above without twelve more strings.

**Nesting.** There are two groups. `work` and `academic` set `parent = "about"` (an entry-level key, _not_ under `[menus.main.params]`), so they render as an indented sub-list under About. **The sub-list is always rendered**, in both variants — Work and Academic are destinations in their own right, not a detail of About, and a menu whose entries appear only once you are already inside the group cannot be used to get there. It was a reveal gated on the group being active until 2026-09; that needed a second boolean, `$childActive`, looping `.Children` explicitly because `/work` and `/academic` are children _in the menu only_ — their URLs are not nested under `/about`, so the parent's `hasPrefix` test could never match them. With the gate gone so is that value; the template now computes one boolean.

The Favorites group differs in one way that is worth knowing: its children's URLs really are nested under the parent's, so on `/favorites/albums/` the parent's `hasPrefix` test matches too and **both rows light up**. That is honest for a nested URL — you are in Favorites and in Albums — and it is the ancestor highlight the About group cannot have. It also puts `aria-current="page"` on two links, which is the pre-existing behaviour of every `/blog/<post>/` page and was left alone rather than fixed as a side effect of this split.

`$isActive` — the entry's own highlight — deliberately omits `HasMenuCurrent`, which would light up About while you are on `/work`. Children are highlighted by an exact `eq $current .URL` instead.

That flat-URL choice is deliberate: `content/<lang>/academic.md` binds to `layouts/academic/single.html` purely by its root-level content path (Hugo v0.146+ matches templates by path). Moving it into a subdirectory to get `/about/academic/` would silently fall back to `_default/single.html` and drop the publications list, unless `type: academic` were added to its front matter.

Sub-menu styling is utilities: the guide line is `border-s border-base-300` on the `<ul>` in `nav-menu.html` (`base-300` because `neutral` is not a divider token in this theme system), and the child variant's smaller size and deeper indent are one branch of the class string in `nav-link.html`. That file used to carry a warning that children must emit _no_ `p-*`/`text-sm`/`font-*` utility, because those would beat the `@layer components` rules that owned the indent; with both sides as utilities the constraint is gone.

Every link carries `border-s-2 border-transparent` whether active or not, so turning the border on does not shift the row by 2px — the same trick `.toc a` still uses. The active tint is `bg-primary/12`, which resolves to the same `color-mix` the hand-written rule used and tracks each theme's own accent with no per-theme override.

### Content Sections & Front Matter Patterns

| Section      | Notes                                                                                                                                                                                                                                                                                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `blog/`      | Page bundles (`slug/index.md`). Front matter: `cover`, `coverCaption`, `tags`, `categories`, `updated`, `disclaimer`, `disclaimerType` (`info`/`success`/`warning`/`error`, default `warning`), `status` (`seed`/`growing`/`living`/`archived` — idea/project maturity, rendered as an emoji via `post-status-emoji.html`/`post-status-badge.html`), `toc`. |
| `photos/`    | Page bundles. Displayed as a masonry grid; individual albums use PhotoSwipe lightbox. Front matter: `cover`, `location`, `camera`.                                                                                                                                                                                                                          |
| `snippets/`  | Page bundles. Front matter: `language`.                                                                                                                                                                                                                                                                                                                     |
| `now/`       | Single hand-edited leaf bundle per language (`content/<lang>/now/index.md`) — no dated history, no `hugo new` archetype. Edit the file directly.                                                                                                                                                                                                            |
| `favorites/` | Only `_index.md` is written by hand. Every page under it is generated from `data/favorites/` by a content adapter — see below. Never `hugo new` here.                                                                                                                                                                                                       |

**`updated` is optional and only renders when it is a _later day_ than `date`.** `layouts/blog/single.html` puts it inline in the meta row between the published date and the status badge, labelled with `post_updated_label` — a shorter key than the `last_updated_label` used by the accent-bar block in `partials/header.html` and `blog/list.html`, which those two keep. The comparison is on `2006-01-02` strings, not `.After`: a date-only `updated:` parses to UTC midnight, so against a same-day `date:` carrying a `-03:00` offset an instant comparison reads it as _earlier_ and silently drops it. The consequence is that a same-day revision cannot be shown — which is the right trade, since the row displays day granularity anyway. Guard every read with `{{ with }}`: `archetypes/blog.md` emits `updated: ""` and `time.AsTime ""` fails the build. Nothing in the list views reads it — the homepage row, the featured card, the archive and `blog-posts.html`'s ordering all key off `.Date`, so an updated post does not resurface.

**`toc: false` works on any single page, not just blog.** The TOC is otherwise automatic — every page routes through `baseof.html`, which asks `layouts/partials/has-toc.html`, and that returns true for any `.Kind "page"` with at least one heading in the `[markup.tableOfContents]` range. Setting `toc: false` suppresses both variants (rail and mobile) _and_ collapses the right rail to its slim track, because all three call sites read that one partial. `toc: true` is inert — it can't manufacture headings.

**`about` / `work` / `academic` are hand-edited root pages**, not sections — `content/<lang>/{about,work,academic}.md`, edited directly like `now.md` and `uses.md`. They split the site's self-description three ways, and the split is the point: `/about` is personal (interests, how I got into IT), `/work` is the engineer (industry intro, `{{< work >}}`, links out to `/projects` and a `/cv.pdf` download), `/academic` is the professor and researcher (`{{< education >}}`, subjects taught, publications). Each shortcode appears exactly once per language — keep it that way, or the same data renders twice. `about.md` and `work.md` fall through to `layouts/_default/single.html`; `academic.md` binds to `layouts/academic/single.html` by path (see **Nav Menu** above). Cross-page links should use `{{< relref >}}` rather than absolute paths — a bare `](/favorites)` resolves to the EN page from the pt-br site and 404s. One exception: `{{< relref >}}` **cannot** be nested inside another shortcode's parameter (`caption="… {{< relref … >}}"` fails the build with "cannot mix named and positional parameters"); use a plain path there.

**`/favorites` is a section, not a root page** — the one place the site departs from the pattern above, and the only section whose pages are generated rather than written. It replaced a single `content/<lang>/library.md` in 2026-09: that page stacked all twelve collections behind twelve `<details>` toggles, and the whole of it lived at one URL you could not link into. Now `content/<lang>/favorites/_index.md` is a card index and each collection is its own page at `/favorites/<collection>`.

**The collection pages are built by a content adapter**, `content/<lang>/favorites/_content.gotmpl` — a one-line wrapper over `layouts/partials/favorites-adapter.html`, which both languages share so the two `contentDir`s cannot drift. The adapter ranges `favorites-categories.html`, the same partial the pages and the index card grid read, so the pages, the cards and the nav children are the same list in the same order by construction. Four things follow:

- **Adding a collection stays "a new YAML file plus two i18n keys and no template edit"**, which is the whole reason it is an adapter rather than 24 content files and 12 `[[menus.main]]` blocks. The new file gets a page, a nav entry and an index card at once.
- **The nav entries come from the adapter, not from `hugo.toml`.** `.AddPage` takes a `menus` key exactly as page front matter does, and each child declares `parent = "favorites"` against the one entry `hugo.toml` still carries. **The menu identifier _is_ the i18n key** (`favorites_category_albums`): `nav-link.html` labels every entry with `i18n .Identifier` and has no fallback, so an entry named anything else renders an empty link.
- **Each child carries its collection's own glyph**, the same `icons/favorites/<key>.html` file the index card uses, so a collection has one icon everywhere it appears. The adapter sets it under the menu entry's `params` (falling back to the star as the index does); a hand-written page sets `menus.main.params.icon: favorites/<key>`. They carried none until 2026-09 on the theory that repeated copies of one glyph would read as noise — which was true of one glyph, and is not of six distinct ones.
- **`list.html` ranges the section's pages, not `data/favorites/`.** The two stopped being the same list when the three prose collections lost their YAML, and a data-driven grid would have dropped them from the index silently. Every collection has a page — the adapter builds one for each remaining data file — so `.Pages.ByWeight` is the complete set in nav order by construction. **A card is an icon, the name and a count**, and deliberately not the page's `description` or a preview of its entries: that renders under the page's own `h1`, and repeating it on the card made the grid read as paragraphs rather than doors. The count is `len .items` for a data-backed collection and `strings.Count "<li>" .Content` for a prose one — the same number as long as the page is written as a list, which all three are. The icons are `layouts/partials/icons/favorites/<key>.html` — solid `currentColor`, unsized, wrapped at `w-6 h-6` here and `w-4 h-4` in the nav — resolved through `templates.Exists` with `default.html` (a star) as the fallback, so a new data file never fails the build for want of a glyph.
- **`layouts/favorites/single.html` renders one collection and `layouts/favorites/list.html` the index.** The item markup — all three shapes — lives in `layouts/partials/favorites-items.html`, the old `library/single.html` block minus its `<details>`/`<summary>` wrapper (on a page whose own `h1` names the collection, a lone collapsible section has nothing to collapse against), extracted so the page can call it once per group. That partial is the file `.prettierignore` names, for the branch-tag shape described under **Formatting**; `single.html` itself formats.
- **`running: true` splits a group once more, into blocks.** Inside each group the on-air entries render first under an "On air" / "No ar" label, then the rest under "Finished" / "Finalizadas" (`favorites_block_running` / `favorites_block_ended`). The Portuguese agrees with _séries_; it only ever shows beside an on-air block, and today only the series group has one — if an anime group ever does, the label lands over _animes_ and is worth revisiting. A group with nothing on air is one unlabelled block: the ended state is the default and only needs naming beside its opposite. `favorites-categories.html` does this split too, as `blocks` on every group, so the page again has no special case. The label is the post card's kicker string, one step below the group's section label. It was a chip on the card for an hour first; the split reads better because the on-air shows are what you come to the page to check.
- **Never `[&+&]:mt-8` for the gap between blocks.** The scanner drops the `+` form silently — verified, the rule never reached the stylesheet — which is the same class of failure as the `>` note under **Styling**. The blocks sit in a `space-y-8` wrapper instead.
- **`columns: 4` fixes the poster grid's count instead of letting it auto-fill.** The default track list packs ~six across at the full column, which suits album art; `tv-shows.yaml` sets four because show art is landscape key art cropped square and at six-up the faces were too small to tell apart. It resolves through a dict of literal class strings in `single.html` (`"4"` → `grid grid-cols-2 sm:grid-cols-4 gap-4` plus a 15px title, against the auto-fill grid's 13px), never by concatenation, so another count is a new dict entry rather than a safelist line. The title size travels with the column count on purpose: a card half again as wide takes a title a step up, or the name reads small under the art.
- **A collection can be split into headed sections without leaving its file.** `groups: [series, anime]` at the top of the YAML plus `group:` on each entry — `tv-shows.yaml` is the one that does, TV series above anime — and the page renders one `section-label.html` heading per group, in the declared order, with the page's own `h1` still naming the whole. The heading text is `favorites_group_<key>` in both i18n files. `favorites-categories.html` does the partitioning and hands every category a `groups` slice, so `single.html` has no special case: a file with no `groups:` is one group with an empty key, rendered unheaded, and an entry with no `group` (or one the file does not declare) lands in that unheaded first group rather than vanishing. `items` stays the flat list for the index card's count.
- **A collection gets prose by growing a real content file**, `content/<lang>/favorites/<key>.md`, and the adapter then stands aside for that key in that language. `articles`, `videos` and `books` have one in both languages; the other five are adapter-only.
- **Those three have no YAML at all any more, and that is the shape to expect.** They were `data/favorites/{articles,videos,books}.yaml` until 2026-09, when their entries were converted into markdown lists inside the pages themselves — dates, links, creators and the `PT` marks folded into the prose. A collection is therefore one of two things and never a blend: **data**, where the YAML owns the entries and the page is generated, or **prose**, where the file owns everything and `favorites-categories.html` has nothing for that key. `single.html` handles the second for free — its `range where … "key" $collection` simply matches nothing. **The skip is not optional and the failure is silent**: a content file and an adapter page claiming one path do not collide and do not warn — the adapter's page simply wins and the file's markdown never appears. That is why the adapter tests `fileExists` rather than letting Hugo sort it out, and why the path is spelled out as `content/<lang>/favorites/` (a template cannot read `contentDir`, so this mirrors `hugo.toml` by hand).
- **A hand-written collection page needs a title, a weight and its menu entry.** `layouts/partials/favorites-page-key.html` resolves a page to its data key — `collection` for an adapter page, the filename for a hand-written one — and both `single.html` and `list.html` call it, so a page cannot resolve to one collection in the card grid and another on the page itself. Its `menus.main` block repeats what the adapter would have declared: `identifier` (the i18n key), `parent: favorites` and a `weight`. **The page `weight` and the menu `weight` are separate values and both matter** — the first orders the index cards, the second the nav — and for a data-backed collection they both have to match the YAML's, which is the one thing kept in step by hand.
- **`description` renders under a hand-written page's `h1`** through `header.html`, so a one-line intro belongs there rather than as a first paragraph. It is not read anywhere else.
- **Only a hand-written page is searchable, and its whole body is.** `data-pagefind-body` is emitted just when `.Content` is non-empty, so the five adapter pages stay out of the index entirely — as the whole of /library was. The data-driven entry lists carry `data-pagefind-ignore` in both card shapes: they are other people's titles scraped into a list, and a search for a book's name should find the book, not this page. A prose collection's entries are markdown and so _are_ indexed, which is the right asymmetry — those are written, not scraped. The `body` wrapper sits _outside_ `header.html` so the `h1` Pagefind titles the result with is inside it, and the back-link is ignored on its own.

**`_index.md` carries `toc: false` and `aliases: ["/picks/", "/library/"]`.** The section has now been renamed three times — Picks → Favorites → Library → Favorites — and **every** old URL must stay in that alias list; dropping one 404s a previously published link. `/favorites/` was itself an alias on the old page and had to come off it, since a real page and an alias cannot claim the same URL.

**`friends.md` is a fourth hand-edited root page** (`content/<lang>/friends.md`), binding to `layouts/friends/single.html` by the same path rule — an old-school blogroll at `/friends`, following the /friends page convention. Like the /favorites pages it holds no entries itself: they come from `data/friends/`, one YAML file per section, each with its own `weight` for section order and an `items` list of `title` / `link` / optional `note`. A section's heading text is `friends_group_<filename>` in both i18n files, so **adding a section is a new YAML file plus two keys and no template edit**; a missing key renders the raw filename rather than failing. Entries carry no `date` — a blogroll is not ranked, and the order inside a section is the YAML order.

**The entries are a plain bulleted list** — `list-disc` on the `<ul>` with `ps-5` for the indent, `link-dash` on the name — and the notes go through the favorites' own `favorites-item-note.html`, so the `note: {en: …, pt-br: …}` map and its `reflect.IsMap` guard apply here unchanged. They were the favorites' ruled list rows (`li` hairlines, `first:border-t-0`) until the bullets landed: a marker and a rule are two separators for one break, and on a blogroll of one-line entries that read as bands rather than as a list. The rule under the section heading is now the only hairline in a section, and the row padding came down with the rules. Two mechanics worth keeping: `list-disc` is required because Tailwind's preflight sets `list-style: none` on every `ul` (preflight zeroes the padding too, so `ps-5` is the whole indent, and it must not be paired with `p-0` — shorthand vs. logical longhand, decided by emission order); and the marker is muted to `/45`, the note separator's value, because a bullet is punctuation and the site's `/70` floor is for text. `marker:` set on the `<ul>` reaches the items — Tailwind compiles the variant to `&::marker, & *::marker`.

**A note is optional, and it runs inline after the name at the name's own size**, separated by the muted `·` the favorites rows' title/creator pair uses — same reasoning as there: a step down in size read as a cramped afterthought, and colour is enough hierarchy on one line. Two consequences. The row passes a `class` to `favorites-item-note.html`, which **replaces** the partial's default string rather than extending it: the default is a 0.75rem block with a top margin, and the two shapes disagree about `display` and `font-size`, so appending would leave the loser of each pair to Tailwind's emission order. The language lookup, the map guard and the empty check stay shared, which is the whole reason the partial is still the one that renders this. And **the `·` belongs to that class string, not to the row** — a name and a link are the whole of an entry now, so a separator written in the template would be left stranded after an entry with no note; the partial renders no element at all when the note is absent or empty, `before:` included.

**The row is not a wrapping `<a>`, and that is the first of two places it departs from the favorites rows.** A friend's note routinely cites where to read them, so it carries markdown links — and `favorites-item-note.html` runs `markdownify`, so those become real anchors. An anchor inside an anchor is invalid HTML: the parser resolves it by closing the outer one at the inner start tag, so the row link silently ends early and the rest of the note falls outside it. There is no error and the page still renders, which is what makes it easy to miss. So only the name is a link and the note's links are ordinary siblings. Three details follow from that. Note links need `[&_a]:underline` — the site-wide `a` rule sets only the decoration's colour and style, and the underline itself comes from prose styling this span sits outside of. The name is plain `inline` — the click target is the name rather than the full row width, and `inline-block` (which it was until the note moved onto the same line) would not share a baseline with a note that wraps past it. And **the row has no accent edge on hover**, which is the second place it departs from the favorites rows: an edge lighting up across a row that is mostly dead space would promise a click that is not there, so the name's dashed underline is the only hover cue. That edge was driven by `has-[a[data-friend-link]:hover]` on an inner wrapper until 2026-09; with it gone the wrapper is gone too (its padding sits on the `li`) and so is the `data-friend-link` hook that kept the note's own links from triggering it.

**The favorites rows have the same latent trap**, since they _are_ a wrapping `<a>` around a markdownified note. No entry in `data/favorites/` uses a link in a note today; the first one that does will break that row the same way, and the fix is this same overlay. The weight sort is inline in the template rather than in a partial, which is the one place this parts company with the favorites pages: `favorites-categories.html` exists because three surfaces read that data and must not disagree about order, and this page is the only reader of `data/friends`.

Work history, education, and papers are **not** content sections — they're Hugo data files under `data/en/` and `data/pt-br/` (`work.yaml`, `education.yaml`, `papers.yaml`), consumed by the `work` / `education` shortcodes in `content/<lang>/about.md` (via `layouts/partials/cv-entries.html`) and by `content/academic.md` (via `layouts/academic/single.html`) through `index hugo.Data site.Language.Lang "<name>"`. There was a standalone `/cv` page (`content/<lang>/cv.md` + `layouts/_default/cv.html`) rendering work and education as a DaisyUI timeline until 2026-08; it was removed and its two sections folded into the about pages, so each data file now has exactly one rendering. They were content page bundles until 2026-07; that caused a nil-map-index build failure once a section had no matching front matter param expected by a shared list partial (`post-status-icon.html`), since these sections had no dedicated list template and fell back to `layouts/_default/list.html`. Data files sidestep the whole page/list-template code path — add new entries as YAML list items, not `hugo new`.

**`data/favorites/` and `data/friends/` are the language-neutral data directories**, and deliberately so. CV entries are prose and genuinely differ per language, hence `data/en/` + `data/pt-br/`; a favorites entry describes a _thing_, and the thing is the same whichever language you read the site in. Entries were content pages split across `content/en/picks/` and `content/pt-br/picks/` until 2026-08, which meant a partial existed purely to merge the two `contentDir`s back together and de-duplicate translations, plus `build: {render: never, list: always}` on every entry for pages that never rendered. Both are gone.

One file per category (`albums.yaml`, `games.yaml`, `people.yaml`, …), each carrying its own `weight` (section order on the page) and `display` — `poster` for things with cover art, `list` for things without (a person worth following has no cover, and forcing one gives a wall of placeholders), and `card` for a horizontal card with the cover on the left and a text block beside it, which is what games use now that a collection page has the room a twelve-up grid never did. **Adding a category is a new file plus one `favorites_category_<filename>` key in both i18n files** — no template edit, no content file and no `[[menus.main]]` block. The content adapter turns the file into a page at `/favorites/<filename>`, a nav child and a card on the index at once. A missing key renders the raw filename rather than failing — in the nav too, where the key doubles as the entry's identifier.

Entry fields: `title`, optional `creator`, `link`, optional `cover` (under `assets/images/favorites/`), optional `date` (sort key, newest first), optional `lang`, optional `note`, optional `group`, optional `running`. Category-level keys: `weight`, `display`, optional `date_label`, optional `cover_ratio`, optional `groups`, optional `columns`. Seven things to know:

- **Cover shape is a _category_ setting too.** `cover_ratio: poster` on `games.yaml` renders its covers at 2:3 — vertical box art, the same shape as a film poster (a storefront capsule is typically 600×900). Unset means `square`, which is the base rule and suits album art. Poster cards use `aspect-ratio` + `object-fit: cover` rather than each cover's natural shape, because within a category the grid has to line up and the sources are whatever the store or label published; a mismatched source is centre-cropped. Adding a shape is one entry in the aspect dict in `favorites/single.html` plus one `cover_ratio:` line — no structural change.

- **There is no `rating` field, and that is the point of the section.** Every entry carried an optional 1–5 star run until 2026-09, when /library became /favorites: a list of favorites is already the top of the scale, so ranking inside it says nothing — and it made the two categories that deliberately carried none (articles and videos, both prose pages now) read as incomplete rather than as a choice. `rating-stars.html` and the `favorites_rating_label` key went with it. Sort order is `date`, and that is the only ordering the data carries.
- **`date_label` is currently unexercised, and is kept anyway.** Its only three users — `books.yaml` (`finished`) and `articles.yaml`/`videos.yaml` (`bare`) — became prose pages in 2026-09, so no remaining category sets it and `favorites-item-date.html` renders nothing anywhere; `favorites_finished_on` and `favorites_finished_in_progress` are unused for the same reason. It is config-driven machinery in the same sense the four empty stub YAMLs are, and it is how a date comes back to any collection. The two bullets below describe it as it works, not as anything renders today.
- **Showing a date is a _category_ setting, not an entry field.** `date_label: finished` renders every entry's `date` as "Finished &lt;date&gt;" via `favorites-item-date.html`, which builds the i18n key as `favorites_<label>_on` — so a new worded label is a new key in both files, no template edit. Unset means no date renders, which is right for most categories: "Finished" under an album is nonsense. There is deliberately **no** separate `finished` field; for a book the date you add it and the date you finished it are the same, and a second field would only be another value to keep in step with the sort key. `favorites-item-date.html` runs `time.AsTime` because an unquoted `2023-10-18` in YAML parses to a time but a quoted `"2023-10-18"` stays a string, and only one of those survives a date formatter.

- **`date_label: bare` is the one label that is not a word**, and the only value the partial special-cases: it renders the date with no leading text. Added 2026-08 for articles and videos, which are prose pages now. A word there would have to say "Read" or "Watched", which claims more than the data knows — the date is when the link was added — and on a list of one-line rows the same word repeated down the column reads as noise rather than as a label. Because it is a sentinel and not an i18n suffix it needs **no keys in either file**, and it has no in-progress state: an article is not something you are part-way through the way a book is. The float in `favorites-categories.html` is not special-cased, so a `bare` entry with no `date` still sorts to the top of its category and renders nothing where the date would be — leave `date` off one only if pinning it there is what you want.

- **An entry with no `date` in a `date_label` category is "in progress".** A book you are still reading has no finish date, so it renders a badge (`favorites_<label>_in_progress` → "Reading" / "Lendo") where the date would go, and `favorites-categories.html` floats it above everything dated — it is the most current thing in the category. So a new _worded_ `date_label` needs _two_ keys in both i18n files, `_on` and `_in_progress` (`bare` needs neither). Dateless entries keep their YAML order among themselves. Splitting the slice before sorting also keeps `sort` away from a nil key.

- **`layouts/partials/favorites-categories.html` is the only reader.** It rebuilds `hugo.Data.favorites` — a map, which Go templates walk in _key_ order, i.e. alphabetically — into a slice sorted by `weight`, drops empty categories, sorts each category's items by date and partitions them into its `groups`. Three surfaces read it — the index card grid, a collection page and the content adapter that builds the collection pages — so none of them can disagree about which categories exist or in what order. Use `sort`, not `.ByDate`: these are plain maps, not pages.
- **Games, albums and TV shows carry no `date` at all, and are ordered by the YAML.** The partial keeps undated entries in file order, so that is the whole mechanism — a hand-ranked list rather than a newest-first one. A `date` on a single entry would float it above the rest of its collection, since dated entries sort ahead of undated ones. No data-backed collection carries one any more; the field survives for the day one wants a newest-first order back.
- **An empty category has no page, no card and no nav entry**, because the partial drops it before any of the four sees it — the same reason it never got a heading on the single page this replaced. `apps`, `hardware`, `people` and `websites` are stubs today and appear nowhere. There was a `movies.yaml` until 2026-09; it was dropped rather than kept as a stub because a film list turns over too fast to be worth maintaining, and its icon went with it.
- **`lang` is explicit, not inferred.** There is no content dir to read it off any more, which is the better design: tag the handful of entries whose _work_ is language-bound (an untranslated book) and readers of the other language get a `PT`/`EN` badge. Nothing needs exempting for being language-neutral, unlike the old directory-inferred version.
- **`note` is a map keyed by language** (`note: {en: …, pt-br: …}`) falling back to `en`. It is the only prose in the data, so it is the only part needing translation. `favorites-item-note.html` guards with `reflect.IsMap` because writing `note: "…"` as a bare string is the obvious mistake and `index` on a string is a build error. Notes render in both card shapes; poster cards pass `clamp` and get `line-clamp-2`, because at ~8.5rem wide an unclamped note would double a card's height and break the grid's rhythm.

**The `card` shape carries three fields the other two ignore**: `genre` (a `text-primary` kicker, the same call the post card makes for its category), `mode` and `platform` (one `·`-separated run on its own row under the genre — "Single-player · PS4"; the two were one line joined by a short rule until the rule was the first thing to wrap at two columns) and an optional `description`. Every one is optional and the separators travel with the piece they follow, so a partial entry never renders a stranded dash. It carried a `tags` chip row briefly in 2026-09 and lost it: on a card that is already a genre, a mode and a platform, three more labels were a fourth way of saying the same thing. It is the poster card's panel plus the list row's hover accent edge — it is a row, so it gets the row's cue — and its cover column is a fixed width that stretches to the card's height, cropping a 2:3 cover under a short text block rather than leaving a strip of panel below it. **Two columns from `md`**: it was one full-width card per row for an hour, and at 56rem the text block — a title and a kicker line — left half of every card empty. ~26rem a card is what a title and a kicker need; the step down if a long title wraps badly is the cover column (`w-32`, up from `w-24` because the art read as a thumbnail), not the grid.

**`link` is optional on every shape, and an unlinked entry is a `div`, never an empty-href `a`** — that is focusable and navigates to the current page. The list row always degraded this way; the poster card learned to in 2026-09, when every TV show lost its link (where a show streams changes too often to keep up with, so `tv-shows.yaml` carries none). The `group`, the hover fill and `no-ext-icon` sit on the anchor branch only, so an unlinked card promises nothing on hover. This is the branch-tag shape `.prettierignore` exists for, now in two places in `favorites-items.html`.

**The two original card shapes are styled in opposite directions, deliberately — do not converge them.** A poster card is a panel: `base-200` surface on the `base-100` main column, `base-300` hairline, shadow, stepping to `base-300` on `:hover`/`:focus-visible`. Cover art is an object and a surface under it says so. A list row is the opposite: no panel, no border, no shadow, rows separated by a single `base-300` hairline (`li + li`), because boxing each line of a text list turns a short list into a stack of heavy tiles. Its hover cue is a 2px accent `border-inline-start` that is always present but transparent, so the text does not shift on hover. Both shapes are a single card-wide `<a>`.

The meta run beside a title is the language chip and the date, and nothing else — `items-baseline` on the row's head, because two boxes of different font sizes centred on each other do not put their text on one line. It held a star run until 2026-09 (see `rating` above), which is what the `self-center` on the badges is left over from: an SVG's baseline is its bottom margin edge, so a baseline-aligned star hung above the x-height and had to be exempted back to centre.

Section headings are a `<details>` + `<summary>` with a `group`, and the chevron is an inline SVG (`icons/chevron-right.html`) rotated by `group-open:rotate-90` — it was a masked `::after` pseudo-element until 2026-09, which a utility cannot express.

### Disclaimer Alerts

`layouts/partials/disclaimer-alert.html` renders the `disclaimer` front-matter string as a DaisyUI alert immediately above `.Content`. It is called from five single templates (`blog`, `_default`, `uses`, `now`, `photos`), each passing `.`, and the outer `{{ with }}` is what makes the archetype's `disclaimer: ""` a no-op. The body goes through `markdownify` — inline markdown only, so a link works but a shortcode or `relref` does not.

`disclaimerType` picks the severity (`info`/`success`/`warning`/`error`, default `warning`). Three things bite:

- **The type is validated before the icon lookup, and has to be.** The icon is resolved with `partial (printf "icons/alert/%s.html" $type)`, the same dynamic pattern as `nav-link.html` and `social.html` — and an unresolvable partial name is a hard build failure. Validating against the slice first turns a front-matter typo into a `warnf` plus a `warning` fallback, the same shape as `mark.html`'s unknown-shape handling.
- **`icons/alert/` is stroke-style at `h-6 w-6`**, unlike every other icon group (`fill="currentColor"`, `w-4 h-4`). DaisyUI's alert layout expects a 24px outline glyph. Keep the four in step; don't "fix" them toward the other convention.
- **The four `alert-*` classes are safelisted in `main.css`** via `@source inline(...)` next to `@source "hugo_stats.json"`. The class is built as `alert-{{ $type }}`, so it exists as a literal string nowhere and no amount of source scanning will find it — see the scanning note under **CSS Pipeline**. Adding a fifth severity means an icon file, a name in the partial's slice, **and** a name in that safelist.

No i18n keys are involved — the alert carries no chrome text, only the author's own string.

### Image Handling

The `responsive-image` partial (`layouts/partials/responsive-image.html`) takes a `src` path, fetches it via `resources.Get`, and outputs a `<picture>` element with WebP + JPEG fallback at the requested width. Images for favorites entries and page covers must live under `assets/images/` so Hugo's asset pipeline can process them.

### Shortcodes

Shortcodes live in `layouts/_shortcodes/` (the Hugo v0.146+ location — **not** `layouts/shortcodes/`).

| Shortcode          | Notes                                                                                                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `responsive-image` | A photo in the site's cover treatment. Params: `src` (required — page-bundle resource or site-wide asset path), `alt`, `caption` (markdown), `width` (source resample px, default `800` — not the displayed size), `class` (replaces the image's classes outright). |
| `mark`             | Hand-drawn annotation behind a phrase. Params: `shape` (`underline` default \| `circle` \| `marker` \| `box`), `color` (`accent` default \| `primary` \| `secondary` \| `warning` \| `error`). Named `mark` because `highlight` is a reserved Hugo built-in.        |
| `image-row`        | Wrapper holding several `responsive-image` calls; lays them out side by side. Takes no params.                                                                                                                                                                      |
| `work`             | Compact one-line-per-entry listing of `data/<lang>/work.yaml`. Param: `heading` (omit for the `cv_work_experience` i18n string, pass a string to override, or `"false"` to suppress when the surrounding markdown already has a heading).                           |
| `education`        | Same, for `data/<lang>/education.yaml` and the `cv_education` i18n string.                                                                                                                                                                                          |

`work` and `education` are both thin wrappers over **`layouts/partials/cv-entries.html`**, which holds all the markup — same shortcode/partial split as `responsive-image`. The partial takes `entries`, `orgField` (`company` for work, `institution` for education — the only structural difference between the two data files) and `heading`. Two constraints:

- **`not-prose` on the wrapper is load-bearing.** These render inside the `prose … max-w-none` wrapper of `layouts/_default/single.html`, which would otherwise put list markers on the entries and prose link styling on the org names.
- **Entries sort by `sort … "endDate" "desc"`, a plain string sort.** That is what floats current roles to the top: the literal `"Present"` (used verbatim in both languages' YAML) sorts above `"2023-12"`. Don't "fix" it into a date sort without replacing that sentinel.

`mark` emits an inline SVG stretched to the phrase via `preserveAspectRatio="none"`, sitting behind the text. Everything lives in `layouts/_shortcodes/mark.html`: one `dict` holds each shape's viewBox, path and the utilities that size its box past the text (`left-[-0.1em] w-[calc(100%_+_0.2em)]` and friends), a second maps the `color` param to `text-accent`/`text-primary`/… Both are dicts of **literal class strings** on purpose — `text-{{ .Get "color" }}` would compile to nothing. Offsets are in `em` so shapes scale with the surrounding font size, and `[vector-effect:non-scaling-stroke]` keeps the line an even weight despite the non-uniform stretch. **Constraint:** the shape is absolutely positioned and cannot follow text across a line break, so the wrapper is `whitespace-nowrap` — use it on short phrases only.

`responsive-image` is a thin wrapper over the **`responsive-image` partial** (`layouts/partials/responsive-image.html`), which resolves the source and emits the `<picture>`; the shortcode adds the `<figure>`, the border classes and the caption. **It renders the same markup as a page's `cover` front-matter figure** — `<figure class="my-10 md:px-10">` around `w-full border-4 border-base-200 shadow-md object-cover`, caption in `mt-2 text-xs text-center text-secondary` — and that agreement is the point: a photo inside a page's prose and the page's own cover are one thing. Change one and change the four single templates that carry the cover figure (`_default`, `uses`, `now`, plus `blog`'s own). Three things to know:

- **`not-prose` on the figure is load-bearing.** `layouts/_default/single.html` and `layouts/blog/single.html` put `prose-img:border-4 prose-img:shadow-md` on every image in content, which would double the border the figure already carries.
- **`width` is the source resample width, not the displayed size.** The image always lays out at `w-full`; `width` only caps what Hugo resizes to, and the partial clamps it to the source's own width rather than upscaling. Pass a smaller value inside `image-row`, where each photo renders at a third of the column.
- **`image-row` strips the child figures' own spacing with `[&_figure]:my-0 [&_figure]:px-0`.** Those land at (0,1,1) and so beat the child's own (0,1,0) `my-10`/`md:px-10` whatever order Tailwind emits them in — no CSS needed. The row stacks to one column below `sm`.

The site had a **polaroid** shortcode until 2026-09 — a framed, tilted print with a caption on a thick bottom strip, plus a `polaroid-group` that piled several into an overlapping row via `nth-child` rules in `main.css`. It was removed, and every call site (`about.md` and `now.md`, both languages) now uses the cover treatment above. Three files went with it (`_shortcodes/polaroid.html`, `_shortcodes/polaroid-group.html`, `partials/polaroid.html`), along with its unlayered `nth-child` block in `main.css`, the `content/en/polaroid-demo.md` draft page and one of the two `.prettierignore` entries.

A demo page for `mark` lives at `content/en/mark-demo.md` — `draft: true`, not in any menu, reachable only at `/mark-demo/` under `hugo server -D`.
